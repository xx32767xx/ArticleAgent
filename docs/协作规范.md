# 协作规范

> **文档编号：DOC-004** · 状态：生效
> 主题：目录怎么分、个人空间规则、分支怎么管、合并请求怎么走、文档怎么写。
> 相关文档：项目总览见 `README.md`，决策见 DOC-002 `docs/决策记录.md`。

## 1. 目录怎么分

```
├── contracts/        公共：接口定义（接口文件 + 样例数据 + 自动检查）    甲、乙
├── docs/             公共：决策、规范、调研、参考材料
├── skills/           公共：三个 Skill（交付物）
│   ├── paper-coach/        3 论文辅导（丙）
│   ├── paper-inspector/    4 论文检测（甲、乙）
│   └── advisor-tracker/    7 导师反馈追踪（丁）
├── rulepacks/        公共：检测规则（甲）
├── servers/tracker/  公共：7 的记录与追踪服务（丁）
├── tools/devkit/     公共：假接口与测试工具（甲）
├── members/          个人空间：a=甲、b=乙、c=丙、d=丁（提交进仓库，但不是交付物）
└── temp/             临时文件（不提交）
```

## 1.1 为什么这么分

先说总的意思:整个仓库就三类东西——**要交出去的**（skills、rulepacks、servers）、**自己干活用的**（members、temp）、**大家共用的**（contracts、docs、tools）。分开摆的原因各不一样:

- **接口定义放最外面（contracts）**:3、4、7 之间只通过接口打交道，接口是唯一的交接面。先把"传什么、回什么"写下来，四方照这个各自开工，不用等对方先把代码写完。接口记在一处，也省得三个人各记一个版本。
- **要不要放文档（docs）单独一份**:决策、接口、平台情况、导航各管一摊，不混在代码里。换人或过几个月回来看，能顺着文档找到"当初为什么这么定"；文档编了号，讨论时可以直接说"按 DOC-003 第 4 节"。
- **三个 Skill 放在一起（skills）**:一个 Skill 就是一个交付物，谁负责哪块一看目录就知道，评审也按目录走，边界清楚。
- **规则单独放（rulepacks）**:规则是要经常改的（规范更新、误报反馈），而写规则的人主要懂规范、不一定懂引擎。规则和引擎之间约定一个统一的规则格式，改规则不用动引擎代码，还能单独做评测、单独回滚。
- **7 的记录服务单独放（servers/tracker）**:因为它不是某个模块的附属品，3 和 4 都要调它，属于"公共设施"。说明书（SKILL.md）和服务代码也分开，以后服务换个形式（比如从本地改成别的），说明书不用大改。
- **假接口放（tools/devkit）**:就为了"对方还没写完，我也能开工"。假接口四个人共用一套，测出来的结果才是一个口径，不会各自对不上。
- **个人空间（members）**:四个人并行干活，总得有个不会跟别人撞车的地方放草稿和试验代码；提交进仓库只是为了备份和互相看，所以规矩写死——不是交付物、不参与打包、公共代码不许依赖它。
- **临时文件（temp）**:过程产物随手放，但不进仓库，主干保持干净。

一句话:**交付物、工作区、公共设施分开摆，接口和文档放在最显眼的地方，谁也不用猜"这个该放哪"。**

## 2. 每个人自己的空间

- 每人有一个 `members/<代号>/`，放自己的东西：
  - `notes/`：个人笔记、设计草稿、想法、学习资料；
  - `sandbox/`：个人试验代码。
- 个人空间会提交进仓库，方便备份，也方便互相参考；但它**不是交付物**，不参与打包。
- 公共代码不要依赖个人空间里的东西，避免以后清理时互相牵连。
- 密码、账号等敏感信息不要放进仓库，放 `temp/` 目录。

## 3. 公共区域

- `contracts/`：接口的定义都放这里，是唯一权威。改动前先和搭档说一声（对方模块的负责人），一起确认后再提交。
- `docs/`：决策记录只往后追加，不删不改；接口有变化就更新接口规范（DOC-003）；平台有变化就更新平台调研（DOC-005）。
- 临时文件一律放 `temp/`。

## 3.1 接口管理（优先级最高的约定）

接口规范（DOC-003）是我们所有约定里优先级最高的一份。原因很简单：3、4、7 之间、以及和另一小组之间，全靠它对接，一处对不上，全线出问题。

**与接口相关的一切，以规范为准。** 如果实现或 SKILL.md 跟规范不一致，先按规范改实现、改说明书；要改规范本身，单独评审、走升版本，并在决策记录（DOC-002）里记一条。不允许"代码先改、文档后补"这种倒着来。

**三层一致性，三处都要对上：**

1. **规范 ↔ 实现**：字段名、工具名、参数、返回值、错误码，和 DOC-003 一字不差；
2. **规范 ↔ SKILL.md**：说明书里的调用示例、参数、返回值，从"工具签名清单"（`contracts/signatures`）抄，不要自己编；
3. **实现 ↔ SKILL.md**：两边互相核对；联调时照 SKILL.md 逐条跑，跑不过就是其中一方的问题。

**保证办法**：维护一份工具签名清单（`contracts/signatures`），规范、SKILL.md、实现都从它抄；自动检查里加一条——SKILL.md 里出现的工具名/命令/参数和清单比对，不一致就报错。

**接口纪律 1：字段只加不改名。** 已发布的接口字段改名，等于所有用它的地方同时报错（3 的代码、SKILL.md 示例、样例数据、对方小组），一定会有一段"新旧混杂"的出错窗口。所以：

- 只追加新字段，旧字段保留；
- 要改名、删字段、改语义，就升版本（如 `v2`），新旧并存过渡，并在决策记录里记一条；
- 每次接口变化，在同一个合并请求里一起改：规范、样例数据、SKILL.md 或实现。

**除接口规范之外，其余由开发者自行维护。** 实现细节、内部结构（比如甲↔乙怎么拆文件、规则表怎么写）、SKILL.md 的具体内容、个人空间怎么用，各负责人自己决定即可，不必逐条报批；只有对外接口（字段、工具签名、SKILL 的对外调用约定）需要守上面的纪律。

## 4. 分支怎么管

- **main**：受保护，只能通过合并请求（PR）进入，永远保持可用。
- **个人分支 `dev/<代号>`**：每人一条常驻分支，日常提交先放在这里；每天顺手把 main 合进来，避免最后解大冲突。
- **自己的空间**：可以随时开 PR 合进 main，不用别人评审，自己点合并即可。建议打开自动合并（auto-merge），检查通过后自动完成，不打断手头工作。
- **公共区域**：必须走 PR，请一个人看一眼（谁都可以，最好是对应目录的负责人）。`contracts/` 和决策条目的改动，要搭档确认。
- **互相约定**：每个人只改自己的空间、自己负责的公共目录；要动别人的地方，先打个招呼。
- **冲突**：个人空间之间不会冲突；公共文件冲突由改动的人解决，复杂时找负责人帮忙，当天解决，不拖到第二天。

## 5. 开合并请求（PR）时

- **谁开**：改动的人自己开，不代开。
- **自己的空间**：不用评审，自己合并；只自查不要太，别夹带公共目录的文件、别带敏感信息。
- **公共区域**：至少一个人看过再合并（1 人评审）。`contracts/` 和决策条目要搭档确认。
- **合并方式**：压缩合并（把一条分支上的多次提交压成一条），主分支历史保持干净。
- **冲突**：作者自己解决。

## 6. 合并前自查

- [ ] 这个 PR 只做一件事（功能、文档、空间别混在一起）
- [ ] 提交信息符合格式（见 §7）
- [ ] 本地相关检查已经跑过
- [ ] 改过接口：样例数据和自动检查一起更新
- [ ] 没有 `temp/` 内容、没有敏感信息

## 7. 提交信息

- 格式：`类型(范围): 一句话`，例如 `feat(inspector): add anchor parser`、`docs(adr): record split decision`。
- 小事勤提交；接口变化单独提交一条，方便回看。

| 路径 | 负责人 | 审查要求 |

## 9. 文档怎么写（面向人阅读）

- 先讲"这是什么、为什么"，再讲"怎么做"；一条规则写清前后关系，不堆术语。
- 英文和缩写第一次出现时给中文解释，比如"自动检查（CI）"、"压缩合并（squash merge）"。
- 能用中文说清楚就用中文：自动检查、样例数据、接口定义、假接口、压缩合并。
- 表格和清单可以留，但每一条要能独立读懂；不要写成一串只对内部人有效的缩写。
- 决策类内容写清楚"当时为什么这么定"，方便以后回看时理解背景。
